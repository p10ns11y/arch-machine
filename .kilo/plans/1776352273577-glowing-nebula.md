# Plan: Next Level System Hardening with Security Remediation Policy

## Goal
Implement advanced security hardening for arch-machine using the strict Security Remediation Policy. Focus on strategic vulnerability remediation that prioritizes security over stability, while minimizing breakage through careful planning and fallback options.

## Current State Analysis
- System: Arch Linux with custom security stack (Lynis, rkhunter, ClamAV, Grype, OSV-Scanner)
- Profiles: minimal, ml-dev, security-dev with varying security levels
- Audit tools: grype, osv-scanner, pip-audit, cargo-audit, vector for monitoring
- Current hardening: systemd timers, security-audit.sh, SBOM generation

## Security Remediation Policy Integration
Follow the strict sequence from policies/security-remediation.md:
1. Audit dependencies for severity and fixes
2. Attempt simple fixes (patch, config, minimal code)
3. Upgrade to latest stable if simple fix insufficient
4. Remove package entirely if upgrade fails or introduces breaking changes
5. For transitive dependencies: rename lock files with -insecure suffix and clear caches

**Breaking Rule**: Only acceptable as absolute last resort when all other remediation options are exhausted.

## Strategic Hardening Plan

### Phase 1: Comprehensive Vulnerability Assessment
1. **System Package Audit**
   - Run grype on entire system (`grype dir:/`)
   - Run osv-scanner on project and system packages
   - Identify critical/high severity vulnerabilities

2. **Dependency Analysis**
   - Audit Python environments (conda, uv, pip-audit --fix if supported)
   - Audit Rust crates (cargo-audit)
   - Audit Node.js packages (npm audit --fix)
   - Check transitive dependencies in lock files

3. **SBOM Enhancement**
   - Generate comprehensive SBOMs for all package managers
   - Implement automated SBOM validation in CI/CD

### Phase 2: Remediation Execution (Non-Breaking Priority)
1. **Simple Fixes First**
   - Apply configuration patches for known issues
   - Update package configurations to mitigate vulnerabilities
   - Implement workarounds that don't require package changes

2. **Strategic Upgrades**
   - Upgrade security-critical packages first
   - Test upgrades in isolated environments
   - Implement rollback plans for failed upgrades

3. **Cache and Lock File Management**
   - Clear vulnerable package caches safely
   - Implement lock file rotation for insecure dependencies
   - Rename lock files with -insecure suffix as per policy

### Phase 3: Advanced Hardening Features
1. **Runtime Security Enhancement**
   - Implement Tetragon for eBPF-based monitoring
   - Configure Cilium network policies
   - Add encrypted storage for sensitive data

2. **Audit Automation**
   - Integrate automated vulnerability scanning in weekly maintenance
   - Implement alerting for new high-severity vulnerabilities
   - Create remediation dashboards

3. **Profile-Specific Hardening**
   - minimal: Basic security with minimal performance impact
   - ml-dev: GPU security, model poisoning protection
   - security-dev: Maximum hardening with Kubernetes security
