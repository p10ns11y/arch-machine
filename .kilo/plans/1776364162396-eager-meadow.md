# Plan: Implement Offline-First Installer with Consent-Based Network Access

## Goal
Modify the arch-machine installer to operate offline-first: disconnect network, check system requirements and dependencies offline, report missing items to user, then request consent before connecting to download and install packages. This enhances security by minimizing network exposure during initial setup.

## Current State Analysis
- **Installer**: Bash script (`install.sh`) with modular architecture using profiles (minimal, ml-dev, security-dev)
- **Requirements Check**: Currently checks internet connection in `check_system_requirements()` in `lib/installer.sh`
- **Package Installation**: Uses pacman for system packages, curl for external tools
- **Dependencies**: Requires yq/jq, sudo, internet access throughout installation
- **Security**: No offline mode - internet required from start

## Proposed Implementation

### Phase 1: Offline Requirements Gathering
1. **Network Disconnection**
   - Add function to disconnect network interfaces at installer start
   - Support multiple disconnection methods (systemctl, nmcli, ifconfig)
   - Graceful fallback if disconnection fails

2. **Offline System Validation**
   - Modify `check_system_requirements()` to skip internet check initially
   - Add offline-only checks: Arch Linux detection, sudo availability, disk space
   - Collect missing system requirements without network

3. **Dependency Inventory**
   - Create new function to scan for required packages/tools without installing
   - Check for: yq/jq, git, curl, package managers (pacman, pip, cargo, npm)
   - Identify missing items and categorize by type (system packages, external tools)

### Phase 2: User Consent and Network Access
1. **Missing Dependencies Report**
   - Display comprehensive list of missing dependencies to user
   - Categorize by: critical (blocks installation), optional (enhances functionality)
   - Show estimated download sizes and installation time

2. **Consent Prompt**
   - Clear security notice about network access for package downloads
   - Option to proceed, abort, or modify installation scope
   - Remember user choice for automated installations

3. **Controlled Network Reconnection**
   - Reconnect network interfaces after consent
   - Verify connectivity before proceeding with downloads
   - Implement timeout and retry logic for network operations

### Phase 3: Installation with Network Access
1. **Staged Installation**
   - Install critical system packages first
   - Download and install external tools
   - Profile-specific module installation

2. **Progress Tracking**
   - Enhanced logging for offline/online phases
   - Clear status indicators for network-dependent operations

3. **Error Handling**
   - Network failure recovery during installation
   - Partial installation cleanup and rollback options

## Technical Implementation Details

### New Functions to Add
- `disconnect_network()` - Safely disconnect network interfaces
- `reconnect_network()` - Restore network connectivity
- `scan_missing_dependencies()` - Inventory missing packages/tools offline
- `display_dependency_report()` - User-friendly missing items display
- `request_network_consent()` - Interactive consent prompt

### Modified Functions
- `check_system_requirements()` - Split into offline/online phases
- `init_installer()` - Add offline validation phase
- `install_package()` / `run_installer_script()` - Add network status awareness

### Configuration Changes
- Add installer flags: `--offline-first`, `--skip-consent`
- Profile configuration for offline-compatible features
- Logging enhancements for offline/online phases

## Security Benefits
- **Reduced Attack Surface**: Minimal network exposure during initial validation
- **User Awareness**: Explicit consent before network access
- **Dependency Transparency**: Clear visibility of what will be downloaded
- **Air-Gapped Preparation**: System can be prepared offline before network access

## Backward Compatibility
- Existing installations continue to work unchanged
- New behavior opt-in via flags or profile settings
- Graceful degradation if offline features fail

## Testing Strategy
1. **Offline Testing**: Test all offline validation without network
2. **Network Disconnection**: Verify safe disconnect/reconnect
3. **Consent Flow**: Test user prompts and consent handling
4. **Installation Verification**: End-to-end testing with various profiles

## Success Criteria
- Installer can complete full validation offline
- User receives clear report of missing dependencies
- Network access only occurs after explicit consent
- All existing functionality preserved
- Installation succeeds after network reconnection

## Implementation Priority
1. Core offline validation framework
2. Network disconnect/reconnect functions
3. Dependency scanning and reporting
4. Consent prompt implementation
